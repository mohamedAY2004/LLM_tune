Lesson 8 · about 25 minutes

Evaluating an extractor

A perfect test score is where evaluation starts, not where it ends.

Your win today

You’ll build an honest before/after table on held-out rows. Then you’ll write your own stress tests, find where the fine-tuned model breaks, and give each failure a name. That list of failures becomes the to-do list for your capstone.

Three kinds of evidence

1 · Training rows vs held-out rows

As in Keras, training accuracy and evaluate() on test data answer different questions. Here both come from score(), run on different rows.

Keras

history = model.fit(x_train, y_train)
history.history["accuracy"][-1]  # seen rows
model.evaluate(x_test, y_test)   # unseen rows

This course

score(tuned, tok, train_sample)  # seen rows
score(tuned, tok, test_rows)     # held-out rows

When I ran the notebook, the table came out like this (valid-JSON rate / field accuracy):

Model40 training rows40 held-out test rows
Base SmolLM2-135M-Instruct0.575 / 0.5670.025 / 0.025
Fine-tuned (Lesson 5 recipe)1.00 / 1.001.00 / 1.00

A score on training rows tells you the model learned what you showed it. It can’t tell you whether it generalizes: a model that memorized the rows would also score 1.00. The held-out test set uses names, cities and phrasings the model never saw. A 1.00 there means the model generalizes, but only to messages from the same generator.

Forty rows is a small test set: one row is 2.5 points. The Hugging Face evaluation guidebook calls 100 samples “usually a minimum” for automatic benchmarks (source). Look at the base row too. It never trained, yet it scored 0.575 on one set and 0.025 on the other. The two sets just aren’t equally hard. So a before/after comparison is honest only when both models are scored on the same rows.

2 · Two metrics, greedy decoding

The valid-JSON rate measures format: does json.loads accept the reply? Field accuracy measures content: what share of name, age and city values match exactly? They catch different failures. The base model in Lesson 1 had the right content in the wrong format. Below you’ll see the opposite: perfect format, wrong content, which only field accuracy catches. A reply that doesn’t parse scores zero fields, so field accuracy can never beat the valid-JSON rate. Report both.

Greedy search “selects the next most likely token at each step” and is the default when nothing else is configured (generation strategies). score() uses greedy decoding (do_sample=False). The same input always gives the same reply, so if the score changes, the model changed. With sampling, two runs of the same model could score differently.

3 · Error analysis: stress tests and failure tags

Real messages don’t come from your generator. A stress test is a message you write on purpose to break the pattern, together with the JSON you expect. I wrote 17. The fine-tuned model passed 9: it handled an age in words (“thirty-two”), a French sentence, chit-chat around the facts, and “Ignore all previous instructions”. It failed 8, and every failing reply was valid JSON. Some of them:

MessageWrong part of the replyTag
I’m Leo, 29."city": "New York"invented
Just moved to Perth, I’m 30."name": "John"invented
Leo from Perth has 3 kids and is 41."age": 3wrong_value
Meet Kofi, 51, from Rio de Janeiro."city": "Rio"wrong_value
Hana Tanaka, 61, São Paulo"name": "Hana"wrong_value
Ines, born in 1990, lives in Quito."age": 19out_of_scope

Each tag names a cause, and the cause points to a fix:

  • format: not valid JSON. Add cleaner examples of the output.
  • invented: the value isn’t in the message, so the model made one up. Every training message contained all three fields, so the model never learned to say null. Add rows with missing fields.
  • wrong_value: the value is there, but the model copied the wrong thing or only part of it. Every training name and city was one word. Add rows with that pattern.
  • out_of_scope: the schema has no right answer. Decide a rule, then put it in the prompt and the model card.

Only count failures you actually observed. I expected the age in words and the French sentence to break the model. Neither did.

Practice

1. Your fine-tuned model scores 1.0 on 40 of its own training rows. What does that number tell you on its own?

  1. It learned the rows it saw
  2. It will handle real user messages
  3. Its held-out score is also high
  4. The test set is too easy

2. For the message “I’m Leo, 29.” the model replies {"name": "Leo", "age": 29, "city": "New York"}. Which tag fits?

  1. Invented: no city in the message
  2. Wrong value: copied the wrong city
  3. Format: the reply isn’t valid JSON
  4. Out of scope: no rule applies

3. Why does score() generate with do_sample=False?

  1. Same input always gives same reply
  2. Sampling cannot produce valid JSON output
  3. Greedy decoding makes the model smarter
  4. Greedy decoding is required by TRL

4. Review (Lesson 3): in the labels tensor, what does a value of -100 at a position mean?

  1. The loss ignores that position entirely
  2. That position holds a padding token
  3. That position’s loss gets subtracted instead
  4. The target is token id -100

5. model, tok, test_rows and a trainer built on model are ready. Put the lines in order for an honest before/after comparison. Two lines don’t belong.

  1. base = score(model, tok, test_rows)
  2. trainer.train()
  3. tuned = score(trainer.model, tok, test_rows)
  4. gain = tuned["field_accuracy"] - base["field_accuracy"]
  5. print(f"field accuracy gain: {gain:+.2f}")
  6. tuned = score(trainer.model, tok, train_rows[:40])
  7. base = score(model, tok, make_rows(40, "test", seed=2))

Score the base model before trainer.train(), because training changes model in place. Scoring the fine-tuned model on train_rows[:40] only shows it learned its own data. The seed=2 line draws different test rows from the fine-tuned model’s, so the gain would mix the effect of training with the luck of the draw.

6. From memory: in an interview you’re told, “Our fine-tuned extractor scores 100% on its test set, so let’s ship it.” What do you check first, and why? Answer in three or four sentences.

First, that the test rows are truly held out and look like real traffic. If they come from the same generator as the training data, 100% only shows the model generalizes within that pattern. Then I’d run stress tests built from realistic messy inputs, such as missing fields, extra numbers, multi-word names and typos. I’d score them greedily on both valid-JSON rate and field accuracy, tag each failure (format, invented, wrong value, out of scope), fix the biggest category with training data, and list the rest as limitations in the model card.
