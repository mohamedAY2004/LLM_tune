Lesson 2 · about 25 minutes

One training step by hand

Write the PyTorch training loop that model.fit() used to hide, and fix the reply that failed in Lesson 1.

Your win today

You’ll write the training loop yourself and run it on a single example. In Lesson 1, SmolLM2-135M-Instruct wrapped its answer in a label, code fences and prose. After 30 training steps, the same model answers the same question with exactly {"name": "Sara", "city": "Cairo"}.

What fit() was doing for you

1 · The loop, line by line

In Keras you call compile once, and fit runs the loop. In PyTorch you write the loop yourself. It’s short, and every line maps to something fit did.

Keras — fit() runs the loop

model.compile(
    optimizer=keras.optimizers.AdamW(5e-5),
    loss=loss_fn)
model.fit(x, y, epochs=30)

# what fit() does for every batch:
with tf.GradientTape() as tape:
    preds = model(x, training=True)
    loss = loss_fn(y, preds)
grads = tape.gradient(loss, model.trainable_weights)
optimizer.apply(grads, model.trainable_weights)

PyTorch + Hugging Face — you write it

optimizer = torch.optim.AdamW(
    model.parameters(), lr=5e-5)

model.train()                  # ~ training=True
for step in range(30):
    out = model(**batch,
                labels=batch["input_ids"])
    out.loss.backward()        # ~ tape.gradient
    optimizer.step()           # ~ optimizer.apply
    optimizer.zero_grad()      # ~ a fresh tape

The PyTorch tutorial calls these three lines the optimization step: backward “deposits the gradients”, step() “adjusts the parameters”, and gradients are zeroed because they “add up”. Optimizing Model Parameters. You hand the optimizer model.parameters(), the tensors it may change, much as Keras uses model.trainable_weights. Then each step has three lines:

  • loss.backward() computes the gradient of the loss for every parameter and stores it in that parameter’s .grad.
  • optimizer.step() uses those gradients to update the weights. AdamW is Adam with weight decay applied separately.
  • optimizer.zero_grad() clears the gradients, for a reason explained in section 3.

2 · Pass labels, get a loss

Hugging Face causal-LM models compute the loss for you: pass labels and read out.loss. For a causal LM, the labels are simply the input tokens. You don’t shift them yourself. Inside the model, the prediction at position t is scored against the token at position t+1:

position:  0             1        2     3     …   62           63
input:     <|im_start|>  system   \n    You   …   "}           <|im_end|>
target:    system        \n       You   are   …   <|im_end|>   \n

“Shifting the inputs and labels to align them happens inside the model.” HF LLM Course, ch. 7.6. The last position (64 here) has nothing after it, so it’s dropped. That’s the same cross-entropy as a Keras classifier with SparseCategoricalCrossentropy(from_logits=True), applied at every position and averaged. The notebook proves it: computing F.cross_entropy(logits[0, :-1], ids[0, 1:]) by hand gives the same number as out.loss. When I ran it, both printed 3.5153.

This loss counts every token, including the system prompt and the question. Lesson 3 shows why you want only the answer.

3 · Two PyTorch habits: train mode and zero_grad

“Evaluation mode is not a mechanism to locally disable gradient computation.” PyTorch autograd notes. model.train() and model.eval() are Keras’s training=True and training=False. They switch layers such as dropout between training and inference behaviour. from_pretrained returns the model in eval mode, so call model.train() before the loop and model.eval() before generating. SmolLM2’s config sets its dropout to 0, so here the switch changes nothing you can see. Do it anyway: many models use dropout, and the LoRA adapters in Lesson 6 have their own. Also, eval() doesn’t turn off gradients. torch.no_grad() does that.

Why zero_grad()? PyTorch adds each new gradient to whatever is already in .grad. That’s deliberate: it lets you sum gradients over several small batches to simulate a bigger one. In a normal loop you clear them after each update. Otherwise every step uses the sum of all past gradients, not the current one. When I left it out, AdamW still got there, but more slowly and less smoothly: the loss after 30 steps was 0.0198 instead of 0.0044.

Practice

1. You call model(**batch, labels=batch["input_ids"]). The labels are the inputs, not shifted. Why does this work?

  1. The model shifts the labels by one internally
  2. The tokenizer already shifted them while encoding text
  3. Causal models predict the current token, not next
  4. The chat template inserts the shift for you

2. What happens if your loop never calls optimizer.zero_grad()?

  1. Each step uses the sum of all gradients
  2. The weights reset to pretrained values every step
  3. PyTorch raises an error at the second step
  4. Nothing changes, because PyTorch clears gradients for you

3. You call model.eval() before generating. What does that change?

  1. Layers like dropout switch to inference behaviour
  2. PyTorch stops recording operations for gradient computation
  3. The optimizer freezes all of the weights
  4. The model and inputs move to CPU

4. Review (Lesson 1): what does add_generation_prompt=True add to the rendered text?

  1. The opening of the assistant’s turn
  2. A default system prompt message first
  3. An end-of-turn token closing the message
  4. Padding up to the maximum length

5. batch is ready and model.train() was already called. Put the lines in order so that each step ends by clearing the gradients. One line doesn’t belong.

  1. optimizer = torch.optim.AdamW(model.parameters(), lr=5e-5)
  2. for step in range(30):
  3. out = model(**batch, labels=batch["input_ids"])
  4. out.loss.backward()
  5. optimizer.step()
  6. optimizer.zero_grad()
  7. out = model(**batch)

Without labels, the model returns logits but out.loss is None, so there’s nothing to call backward() on. The optimizer is created once, before the loop. Created inside the loop, it would throw away AdamW’s running averages at every step.

6. From memory, as if in an interview: “Walk me through one training step for a causal LM in PyTorch. What did Keras’s fit() do for you that you now write yourself?”

Put the model in train mode. Run a forward pass with labels set to the input ids. The model shifts them internally and returns the mean cross-entropy of predicting each next token. loss.backward() computes the gradients into each parameter’s .grad, optimizer.step() updates the weights (AdamW here), and optimizer.zero_grad() clears the gradients, because PyTorch accumulates them. fit() did all of this for every batch: the forward pass in training mode, the gradient tape, the optimizer update, and the loop itself. For generation, switch to model.eval() and wrap the call in torch.no_grad().
