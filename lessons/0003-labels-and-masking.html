Lesson 3 · about 25 minutes

Labels & masking

Tell the loss which tokens count, so the model learns the answer and not the question.

Your win today

You’ll build labels that hide the prompt behind -100, so the loss counts only the 23 answer tokens of an 84-token example. Then you’ll train on eight examples and see the proof: the loss on the answer collapses, while the loss on the prompt stays put.

Choosing what the model learns

1 · Lesson 2 trained on the question too

In Lesson 2 the labels were the whole input, so the loss counted every token: the system prompt, the user’s message and the answer. Take the first training row from our task. The model predicts 83 of its 84 tokens (position 0 has nothing before it), and only 23 of those are the answer: the completion tokens. The rest are prompt tokens.

Predicting the prompt is wasted effort. At inference time the user supplies the prompt, so nobody needs the model to write it. It also blurs the number you watch. Before training, the loss over all tokens was 3.06, but over the answer alone it was 0.16. The big number was mostly prompt.

Worse, it changes what gets learned. When I trained eight rows with unmasked labels, the loss on the prompt fell from 4.17 to 0.26: the model had learned to predict the instruction and the system prompt. With the prompt masked, an otherwise identical run left it at 4.10.

2 · -100 means “skip this position”

“Specifies a target value that is ignored and does not contribute to the input gradient.” The default is ignore_index=-100. PyTorch CrossEntropyLoss. PyTorch’s cross-entropy has an ignore_index, and its default is -100. A target of -100 adds nothing to the loss or the gradients, and the mean is taken over the remaining tokens. Hugging Face models pass your labels to that loss, so a label of -100 means “don’t learn this token”. Setting the prompt’s labels to -100 is called a loss mask. The recipe:

full = tok.apply_chat_template(prompt + completion,
          return_tensors="pt", return_dict=True)
prompt_len = tok.apply_chat_template(prompt, add_generation_prompt=True,
          return_tensors="pt", return_dict=True)["input_ids"].shape[1]

labels = full["input_ids"].clone()    # a copy, not the same tensor
labels[:, :prompt_len] = -100         # hide the prompt
loss = model(**full, labels=labels).loss

Why does the prompt’s length mark the boundary? Rendered with add_generation_prompt=True, the prompt is exactly the start of the full conversation, ending with <|im_start|>assistant and a newline. Everything after it is the answer, including the closing <|im_end|>, which teaches the model to stop.

PositionsTokenslabels
0 – 60system prompt, user message, <|im_start|>assistant ⏎-100
61 – 83{"name": "Kenji", "age": 66, "city": "Oslo"} <|im_end|> ⏎same as input_ids

Collators pad labels with -100, which “will be automatically ignored by PyTorch loss functions”. Data collators. Two details. First, clone. labels = input_ids is a second name for the same tensor, so writing -100 into it corrupts the inputs too. When I tried that (on CPU), the forward pass crashed with IndexError: index out of range in self. Second, padding. When rows of different lengths are batched, the pad positions get -100 too. Data collators do that for you.

3 · What comes next

“By default, the trainer computes the loss on the completion tokens only, ignoring the prompt tokens.” TRL SFT Trainer docs, “Train on completion only”. TRL, Hugging Face’s library for fine-tuning chat models, has an SFTTrainer that builds exactly these labels for prompt-completion data. When I ran it on our first training row, its processed labels matched the hand-built ones token for token. Lesson 5 hands the job to it.

Practice

1. A position’s label is -100. What happens there during training?

  1. It adds nothing to the loss or gradients
  2. The model predicts a padding token there instead
  3. Its loss is multiplied by negative one hundred
  4. The tokenizer drops that token before the forward

2. How do you find the position where the completion starts?

  1. Token count of the prompt plus assistant opener
  2. Length of the completion rendered on its own
  3. Position of the first <|im_end|> in the sequence
  4. Half the length of the full tokenized conversation

3. You write labels = input_ids, then labels[:, :n] = -100. What happens?

  1. input_ids gets -100 too, so the forward crashes
  2. It works, since labels and inputs are separate
  3. The answer gets masked instead of the prompt
  4. PyTorch copies the tensor automatically before the write

4. Review (Lesson 2): after loss.backward(), where are the gradients stored?

  1. In each parameter’s .grad attribute
  2. Inside the loss tensor’s grad_fn
  3. In the optimizer’s internal state
  4. Inside the model’s config object

5. row and prompt_len are ready. Order the lines to train one step on the answer tokens only. Two lines don’t belong.

  1. full = tok.apply_chat_template(row["prompt"] + row["completion"], return_tensors="pt", return_dict=True)
  2. labels = full["input_ids"].clone()
  3. labels[:, :prompt_len] = -100
  4. loss = model(**full, labels=labels).loss
  5. loss.backward()
  6. labels = full["input_ids"]
  7. labels[:, prompt_len:] = -100

Without .clone(), labels and full["input_ids"] are the same tensor, so masking would write -100 into the inputs and crash the forward pass. labels[:, prompt_len:] = -100 masks the answer, which leaves the model learning only the prompt: the opposite of what you want.

6. From memory, as if in an interview: “What is a loss mask in SFT, and how would you build one for a chat example?”

A loss mask decides which tokens count in the loss. In SFT you usually train on the completion only, because the prompt is always given at inference and learning to predict it wastes updates. To build it, render the full conversation with the chat template and get input_ids. Render the prompt alone with add_generation_prompt=True: its length is where the answer starts. Clone input_ids into labels and set the prompt positions (and any padding) to -100, cross-entropy’s default ignore_index. The model shifts the labels internally, so the loss covers only the answer tokens, including the end-of-turn token. TRL’s SFTTrainer does this by default for prompt-completion data.
