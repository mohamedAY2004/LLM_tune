Lesson 7 · about 25 minutes

QLoRA: a 1.7B model on a free GPU

Store the frozen model in 4 bits, train LoRA on top, and fit a 1.7B fine-tune on a free GPU.

Your win today

You’ll fine-tune SmolLM2-1.7B-Instruct, almost 5× Lesson 6’s model, on a free Colab T4. Before loading anything, you’ll predict its memory with arithmetic. Then you’ll measure it and see why it fits.

Why it fits

1 · Memory math: count the bytes

Hugging Face’s GPU memory anatomy guide: mixed-precision weights take 6 bytes per parameter (a 16-bit working copy plus a 32-bit master copy), AdamW’s two states take 8, and gradients take 4. Training memory is mostly bytes per parameter × number of parameters. A full fine-tune in mixed precision with AdamW keeps weights, gradients and two optimizer states for every parameter. That adds up to about 18 bytes per parameter, before activations.

What’s storedBytes per parameterSmolLM2-1.7B
Weights in fp3246.8 GB
Weights in fp16 or bf1623.4 GB
Weights in 4-bitabout 0.5about 0.85 GB
Full fine-tune, mixed precision + AdamWabout 18about 31 GB

A T4 has 16 GB, so a full fine-tune of this model can’t fit. QLoRA (quantized LoRA) cuts the bill twice. First, the frozen weights are quantized: stored as 4-bit numbers plus one scale per block of 64 weights, about 0.85 GB in total. Second, as in Lesson 6, the 18-byte cost applies only to the LoRA adapters, about 1% of the parameters.

Activations are values the forward pass saves for the backward pass. They grow with batch size × sequence length, and section 3’s knobs target them. When I loaded SmolLM2-1.7B in 4-bit, get_memory_footprint() reported 1.01 GB. That’s a little above the estimate, because the embedding table stays in 16-bit.

2 · Load in 4-bit with BitsAndBytesConfig

from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,                      # store linear-layer weights in 4 bits
    bnb_4bit_quant_type="nf4",              # NormalFloat4, the QLoRA data type
    bnb_4bit_use_double_quant=True,         # also compress the scaling constants
    bnb_4bit_compute_dtype=torch.float16,   # the T4 has no bf16
)
model = AutoModelForCausalLM.from_pretrained(
    model_id, dtype=torch.float16,          # embeddings + norms (not quantized)
    quantization_config=bnb_config)

The QLoRA paper introduced NF4 and double quantization, and fine-tuned a 65B model on one 48 GB GPU. Knob-by-knob details: Transformers bitsandbytes guide. NF4 (4-bit NormalFloat) is a 4-bit format built for roughly normally distributed weights, as trained weights are. Double quantization also quantizes the per-block scales, saving about 0.4 bits per parameter. The compute dtype is what weights are unpacked into for each matrix multiply: float16 on a T4.

The 4-bit weights stay frozen. Gradients flow through them into the LoRA adapters, so your Lesson 6 code barely changes: a LoraConfig (rank 16 today) passed as peft_config=. Three practical details:

  • On a T4, set bf16=False, fp16=True in SFTConfig: fp16 mixed-precision training.
  • For 4-bit models, TRL 1.15 casts the adapters to bf16, and fp16 training then crashes (NotImplementedError: ... 'BFloat16'). The notebook upcasts them to fp32, a three-line fix.
  • Old blog posts call from_pretrained(..., load_in_4bit=True). In v5 that raises a TypeError.

3 · Knobs when memory is tight

KnobWhat it trades
per_device_train_batch_size 1–4 + gradient_accumulation_stepsFewer activations at once. Gradients from several small batches are combined into one optimizer step, so the effective batch (batch × steps) stays the same. Slower.
gradient_checkpointing=TrueKeeps only some activations and recomputes the rest in the backward pass. On by default in SFTConfig. Slower.
max_lengthCaps tokens per example, so caps activations. Too short cuts off the completion.

Keras 3 has the same accumulation idea: keras.optimizers.Adam(gradient_accumulation_steps=4) (Keras Adam docs). More knobs: TRL’s Reducing memory usage and the gradient checkpointing guide. Measure, don’t guess: model.get_memory_footprint() after loading, and torch.cuda.max_memory_allocated() after training. Call torch.cuda.reset_peak_memory_stats() just before training so the peak covers the training run alone.

Practice

1. Using the 18-bytes-per-parameter rule, roughly how much memory does a full fine-tune of a 1B-parameter model need with AdamW, before activations?

  1. About 18 GB
  2. About 4 GB
  3. About 2 GB
  4. About 0.5 GB

2. Why does the T4 notebook set bnb_4bit_compute_dtype=torch.float16 rather than torch.bfloat16?

  1. The T4 has no native bfloat16
  2. float16 uses less memory than bfloat16
  3. NF4 only works with float16 compute
  4. bfloat16 cannot train the LoRA adapters

3. Training crashes with CUDA out-of-memory at per_device_train_batch_size=8. Which change cuts memory but keeps the same effective batch size?

  1. Batch size 2, accumulation steps 4
  2. Batch size 8, checkpointing turned off
  3. Batch size 2, double the max_length
  4. Batch size 4, double learning rate

4. Review (Lesson 6): LoRA with r=8 on one 960 × 960 linear layer. How many trainable numbers does it add?

  1. 15,360
  2. 921,600
  3. 7,680
  4. 1,920

5. On a T4: args (with bf16=False, fp16=True), peft_config, train and tok are ready. Put the lines in order to QLoRA-fine-tune. Two lines don’t belong.

  1. bnb_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_compute_dtype=torch.float16)
  2. model = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.float16, quantization_config=bnb_config)
  3. trainer = SFTTrainer(model=model, args=args, train_dataset=train, processing_class=tok, peft_config=peft_config)
  4. for p in [q for q in trainer.model.parameters() if q.requires_grad]: p.data = p.data.float()
  5. trainer.train()
  6. model = AutoModelForCausalLM.from_pretrained(model_id, load_in_4bit=True)
  7. bnb_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.bfloat16)

The upcast line must sit between building the trainer and training: TRL casts the adapters to bf16 when it builds the trainer, and fp16 training crashes on bf16 gradients. Transformers v5 removed the load_in_4bit=True argument of from_pretrained. Quantization settings now go in a BitsAndBytesConfig passed as quantization_config=. The bfloat16 config is the right shape for newer GPUs, but the T4 has no native bf16, so compute in float16. It also leaves out NF4, which is the 4-bit type you want for training.

6. From memory: in an interview you’re asked, “How would you fine-tune a 7B model on one 16 GB GPU?” Walk through the memory in two or three sentences.

A full fine-tune needs about 18 bytes per parameter with AdamW, so roughly 126 GB for 7B, which is impossible. Even plain LoRA keeps 16-bit weights, about 14 GB, which leaves almost nothing for activations. With QLoRA the frozen weights are stored in 4-bit NF4 (about 3.5 GB), only the small LoRA adapters get gradients and optimizer state, and I’d control activations with a batch of 1–2 plus gradient accumulation, gradient checkpointing and a sensible max_length, checking torch.cuda.max_memory_allocated() after a short run.
