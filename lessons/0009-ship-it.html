Lesson 9 · about 25 minutes

Ship it: your model on the Hub

Merge the adapter, push the model with an honest model card, and let anyone load it by name.

Your win today

Your fine-tuned extractor goes on the Hugging Face Hub with a model card, and anyone can load it in three lines. You’ll also prove that merging and saving didn’t change the scores.

From a Colab session to a public model

In Keras you’d save one .keras file. A Hugging Face checkpoint is a folder: config, weights, tokenizer files and a README.md. The Hub stores that folder as a git repo with a name like you/smollm2-360m-json-extractor.

Keras

model.save("extractor.keras")
model = keras.models.load_model(
    "extractor.keras")

Hugging Face

model.save_pretrained("folder")
model.push_to_hub("you/extractor")
model = AutoModelForCausalLM \
    .from_pretrained("you/extractor")

1 · Adapter or merged model?

Lesson 6 saved only the LoRA adapter. To use it, you load the base model and attach the adapter. merge_and_unload() adds each adapter product B·A into the frozen weight it belongs to, then returns a plain Transformers model with no adapter left:

from peft import PeftModel
base = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.float32)
merged = PeftModel.from_pretrained(base, adapter_dir).merge_and_unload()

When I ran the notebook, both versions scored 1.00 / 1.00 on the 40 held-out rows. Here’s what differed:

AdapterMerged model
File size (fp32)17 MB1,447 MB
To load it you needthe base model + PEFTTransformers only
Scoring 40 rows on my GPU54 s28 s

The PEFT docs say an unmerged adapter adds “inference latency”, and recommend merge_and_unload() to remove it (LoRA reference). I got the same 2× gap with a freshly loaded adapter, so it isn’t a leftover from training. Ship the merged model when anyone should be able to use it with plain Transformers. Ship the adapter when size matters, or when you serve many tasks on one base model. Either way, re-score after merging. The notebook checks that the reloaded model’s scores match the adapter’s exactly.

2 · Push: account, token, one call per object

You need a free Hugging Face account and an access token (a password for programs, not a text token) with the Write role. A Read token can download but can’t push.

The huggingface_hub quick start: “Define a HF_TOKEN secret to be automatically authenticated!” (quick start). Token roles are explained in User access tokens. In Colab, store the token as a secret called HF_TOKEN (key icon in the sidebar) and switch on notebook access. huggingface_hub finds it automatically, so the token never appears in your notebook. Then:

shipped.push_to_hub(repo_id)   # creates the repo if needed, uploads weights + config
tok.push_to_hub(repo_id)       # tokenizer files, including the chat template
card.push_to_hub(repo_id)      # README.md, last (see below)

Push the tokenizer too. The chat template lives in it, and without the template nobody can format prompts the way you trained (Lesson 1).

3 · The model card

The card is the repo’s README.md, and it’s the first thing a user or interviewer reads. It has two parts. A YAML block at the top holds machine-readable metadata. base_model links your model to its parent on the Hub. Below it is plain Markdown for people:

  • What it does, plus a three-line usage example.
  • Training data: what it is and how many rows.
  • Evaluation: your before/after table, with the real numbers from Lesson 8’s method.
  • Intended use and limitations: your failure tags in plain words.

base_model metadata “will be used to display the base model on the model page” and lets users find models derived from it (Hub docs). The notebook builds the card as an f-string, so the numbers come straight from your variables, and wraps it in huggingface_hub.ModelCard. Two traps. Don’t indent the --- lines, or the metadata is silently dropped. And push the card last: push_to_hub on a model writes its own README.md when the repo has none.

Do it: the exercise notebook

  1. Create a free account and a Write token, then add it as the Colab secret HF_TOKEN. The notebook’s first cell shows where.
  2. Download 0009-ship-it.ipynb, then in Colab use File → Upload notebook.
  3. Runtime → Change runtime type → T4 GPU.
  4. Fill in the four # TODOs: merge, save, write the card’s limitations, push. Each has a check cell. Without a token, the push check stays ❌, which is honest.
  5. Run the final cell. It loads your model by repo id, in three lines.

When I tested the notebook on a laptop GPU (RTX 3050 Ti) without a token, it ran in about 3 minutes, with a 2.9 GB memory peak. The base model went from 0.55 / 0.55 to 1.00 / 1.00, and the last cell replied {"name": "Kwame", "age": 34, "city": "Kumasi"}. I didn’t run the push itself: it needs your account.

Practice

1. What does PeftModel.from_pretrained(base, adapter_dir).merge_and_unload() return?

  1. A plain Transformers model, no adapter
  2. Just the adapter’s two small matrices
  3. A PeftModel with adapters still attached
  4. A quantized copy of the model

2. push_to_hub fails with a permission error. Which credential does pushing need?

  1. A token with the Write role
  2. A token with the Read role
  3. No token, public repos are open
  4. Your Hugging Face account login password

3. What does base_model: in the model card’s YAML block do?

  1. Links your model to its parent
  2. Downloads the base weights at load
  3. Merges the adapter on the Hub
  4. Sets the license for your model

4. Review (Lesson 6): after SFTTrainer(..., peft_config=LoraConfig(r=8, target_modules="all-linear")), which parameters have requires_grad=True?

  1. Only the small LoRA adapter matrices
  2. Every weight in the base model
  3. Only the embedding and output layers
  4. Attention layers only, MLPs stay frozen

5. base, adapter_dir, out_dir, repo_id and card_text are ready. The repo doesn’t exist yet. Put the lines in order to ship exactly the model you saved, with your card as its README. Leave the tokenizer out of this exercise. Two lines don’t belong.

  1. merged = PeftModel.from_pretrained(base, adapter_dir).merge_and_unload()
  2. merged.save_pretrained(out_dir)
  3. shipped = AutoModelForCausalLM.from_pretrained(out_dir)
  4. shipped.push_to_hub(repo_id)
  5. ModelCard(card_text).push_to_hub(repo_id)
  6. merged = base.merge_and_unload()
  7. merged = PeftModel.from_pretrained(base, adapter_dir)

base is a plain model with no adapter attached, so it has no merge_and_unload() method. Attach the adapter first with PeftModel.from_pretrained. But that line alone gives you base + adapter, not a merged model: pushing it would upload only the adapter. The card goes last: ModelCard.push_to_hub can’t create a repo, and a model push into an empty repo writes an automatic README.

6. From memory: an interviewer asks, “You fine-tuned with LoRA. Do you ship the adapter or a merged model?” Answer in three or four sentences.

It depends on the users. A merged model (merge_and_unload()) is standalone: it loads with plain Transformers or pipeline, and has no adapter overhead at inference, but it’s full size (1.4 GB in fp32 for a 360M model). An adapter is tiny (17 MB here) and lets you swap many tasks on one base, but users need the base model and PEFT. Either way, I re-score after merging to prove nothing changed, and publish the card with base model, data, before/after metrics and limitations.
